A ticket becomes
a workspace.

Bring the requirements, repository threads, and application services into the same place. Here’s what that looks like in the actual app.

Ticket ↓Setup ↓Build ↓Services ↓

Captured from the current application with fictional tickets and isolated sample repositories. The real orchestration runs against test stubs for Maven, WildFly, npm, and the JDK; these captures do not demonstrate a company build or deployment.

The context stays with the work.

One ticket, four repositories.
A separate thread for each.

Start with the requirements

The selected ticket keeps its release, version, description, and acceptance criteria beside the work. The developer can return to the brief without changing tools.

Keep repositories connected

A whole-ticket checkout prepares its repository worktrees. Each has a coding-agent thread, while the ticket remains the shared reference. These sample worktrees and threads were created by the actual backend.

Review the whole workspace.

Ticket branches, release,
database, and deployable artifacts.

Choose when to start services

Prepare the worktrees first, or build and start the application. Existing matching checkouts and threads can be reused; the rest are created as part of setup.

Keep the release context

Review the selected release, database, backend connection, and EAR modules together before execution. Repository threads share the same ticket Stack.

Inspect the build before it runs.

Changed, Full build,
or an explicit module selection.

Understand what will run

Build previews explain module selection. Changed mode considers module inputs and affected consumers; full and selected builds provide explicit control.

Keep compilation separate from deployment

Build only compiles. Build and run deploys after success. Module results, output, diagnostics, and previous attempts remain inspectable in the Build view.

Know what’s running.
And where.

Build steps, service ports,
and the frontend’s backend.

Inspect the sequence

The Services view exposes provisioning progress; the All steps control expands the worktree, build, deployment, and startup sequence. HTTP, management, and debug ports stay visible alongside the dev server and database.

Make ownership explicit

The frontend can target the Stack’s own application server or a configured backend. The actual orchestration creates isolated worktrees and instances, assigns ports, and follows deployment and readiness markers. External executables are test stubs; this capture does not establish that a real Maven build or WildFly deployment succeeded.
